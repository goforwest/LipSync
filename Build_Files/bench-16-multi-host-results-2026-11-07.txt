== THE HEADLINE ================================================================

The wrong-host race (B4) is SOLVED on the device side. Final mechanism
(shipped in 4.8.14-4.8.16): on every switch, the device disconnects the old
host and holds a 60-second OPEN-advertising window in which ANY non-target
connect is dropped immediately by the firmware ("the bouncer" — one bounce
per connection, no SD filtering dependence). The target joins whenever its
own reconnect engine chooses to; the window cannot strand the radio (hard
60 s bound, then stock behavior).

Per-OS contract (all bench-proven tonight):
  macOS   : fully automatic. Reconnects in ~1 s whenever open advertising
            is available; during a window aimed at another host it is held
            off (one bounce, then it stops trying for ~60 s — backoff).
            Per-switch switches to the Mac: 4/4 cycles flawless.
  Windows : joins the window ONLY when its pairing state is fresh
            (just-re-paired: connected in 0.9 s — bench-proven once) or when
            nudged (one click in Bluetooth settings; forget+re-add when its
            state degrades after churn). It did NOT respond autonomously to
            open OR directed advertising in 60 s windows, with Advanced
            discovery + Best-performance power mode set. Windows-side
            behavior, not a device limitation (exhaustively proven — below).
  iOS     : untested tonight (unpaired; re-pair for future B6 rounds).

== THE ORIGINAL RACE, AND THE TRIAL LADDER =====================================

Original B4 failure (pre-contingency, 4.8.2): switch away from the Mac
0/5 — macOS reclaims the link sub-second, before the target can connect.

Device-side mechanisms tried, in order (each verdict earned on the wire):

1. WHITELIST + OPEN ADVERTISING      — FORBIDDEN by S140 6.1.1: adv_set_configure
                                       refuses with 0x3201 = BLE_ERROR_GAP_
                                       DISCOVERABLE_WITH_WHITELIST ("use of
                                       whitelist not permitted with discoverable
                                       advertising"). Legacy PDUs have no
                                       connectable-non-scannable-undirected type,
                                       so the design doc's Q4 whitelist contingency
                                       is not implementable as specced on this
                                       stack. (Also decoded: 0x3202 is
                                       INVALID_BLE_ADDR — our first decode was off
                                       by one; the entry type/bytes coercion was
                                       still needed and is kept.)
2. DIRECTED ALONE (high-duty, target identity) — the Mac's reconnect is
                                       SUPPRESSED entirely (it ignores packets
                                       addressed to another host — good!), but
                                       WINDOWS IGNORES DIRECTED PACKETS TOO.
                                       (Fair trial finally completed in 4.8.17
                                       against a healthy-ish Windows.)
3. DIRECTED + WHITELIST FILTER       — S140 does NOT enforce either the directed
                                       target field or the whitelist on directed
                                       sets: macOS's connect-by-address walked in
                                       (bench 4.8.9).
4. OPEN + BOUNCER (final mechanism)  — WORKS. The lockout cannot come from the
                                       controller; it comes from our disconnect.
                                       (4.8.12-4.8.16 hardening: one connection =
                                       one bounce — the SD takes ~200 ms to tear
                                       a link down and the millisecond tick spun
                                       600x against the same dying handle before
                                       per-connection tracking; the disconnect
                                       rc is ignored because it races the peer's
                                       own teardown; the storm cap bounds a
                                       persistent non-target.)
5. DIRECTED, FAIR TRIAL (4.8.17)     — Windows still silent. Device side
                                       EXHAUSTED.

Windows-side knobs tried (with the user's consent, after device exhaustion):
  Bluetooth settings page held open       — no effect in 60 s windows.
  Discovery: Default -> Advanced          — no effect.
  Power mode: Best performance            — no effect.
  (Power Management tab absent on this adapter's driver.)
  FORGET + RE-PAIR (the decisive one)     — Windows reconnects SUB-SECOND while
                                            fresh; degrades to silent after churn.

== MAC-SIDE FINDINGS ===========================================================

- Reconnect: aggressive (~1 s) whenever open advertising is available.
- After ONE bounced connect, macOS stops retrying for ~60 s (its own backoff) —
  which is why the bouncer only ever needed 1-3 bounces per window.
- "Connected but no HID" class (seen 3x after heavy churn/switch sequences):
  the link is up, live view is healthy, no cursor. Fixes observed, in order of
  gentleness: Mac Bluetooth toggle (worked once), Mac REBOOT (worked),
  full forget + re-add on BOTH sides (worked; the sour state survived a BT
  toggle alone the final time). Device side exonerated every time (live view
  + wire state healthy). NOTED FOR SHIP: a device-side self-heal is possible —
  if a connection exists but the HID subscription does not enable within a few
  seconds, cycle the link. Not implemented tonight; queued.
- Bond-type/bytes: the Mac's bond stores PUBLIC for an 11-marker-high address
  (S140 validates upper-bits-vs-type on list entries) — lsHostCoerceAddrType
  reconciles type to bytes before any list/directed use (kept in 4.8.7+).
