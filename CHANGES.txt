Version 4.5.0 | 2026-Oct-15
- Added external switch action remapping (upstream #20 — roadmap item 11's deliberately separate follow-up; a clinician's ask: the assistive switch jacks mapped to functions different from sip & puff, and separately mappable per host): the MOUSE- and GAMEPAD-mode action cells of the three switch jacks are now settings — a caregiver can map, per jack and per hold window (short/long/very-long), which output action each switch triggers, from the same action vocabulary the compiled defaults use (nothing, the clicks, drag, scroll, the gamepad buttons B1-B8, cursor centering, the speed steps, mode change and menu open). Everything else stays compiled by design: the menu-mode and safe-mode columns (menu navigation is a fixed language — remapping it could strand a user outside the menu), the S1+S3 combination row, and the time windows themselves (the input timing settings from 4.4.0 remain the routing)
- Wire surface: six endpoints — SA/SB/SC = jacks 1/2/3 mouse mode, GA/GB/GC = the same jacks in gamepad mode. The GET answers "short,long,max" (the actions in force); the SET takes 0 (reset to the compiled factory mapping) or 100000 + short*10000 + long*100 + max (the base keeps every non-reset value a 6-digit number, the one magnitude the serial format validator accepts), with every cell pinned to a caregiver-safe allowlist — deliberately excluded: joystick calibration, menu navigation, software reset and factory reset, so one accidental press of a remapped switch can never erase settings or restart the device. Stored 0 = the compiled default (a settings file written by older firmware reads 0 for the missing keys, so updating keeps the factory mapping); the endpoints join the EX,0:0 dump and the factory-reset defaults
- Remapped actions flow through the same seams the compiled ones do: the 4.4.0 restriction gates still apply (a remapped mode change obeys the mode lock, a remapped menu open obeys the buttons-only restriction) and the input-state LED tier and engage tones behave exactly as for any other action. LipSync Connect (4.5.0-gated) exposes the mapping as its External switch actions card — the caregiver surface the issue asked for; the Hub menu deliberately does not (an 18-cell remap grid is not a mouthpiece-driven OLED menu)

Version 4.4.0 | 2026-Oct-14
- Added input & mode restrictions (upstream #21 #44 #68 #77, roadmap item 11): four stored booleans, all defaulting to the unrestricted legacy behavior — SD disables sip & puff entirely (the pressure state machine and diagnostics keep running; a gated input produces no action, no LED, no cue), MA restricts menu open/close/navigation to the hub buttons, LK locks the operating mode against every input path (the Hub menu's Mode page refuses with a short error cue; the serial API stays open on purpose so a caregiver can always adjust the device through LipSync Connect), and CF freezes the cursor while a mouthpiece input is in progress. The gates live at the single seam every resolved input action passes through; surfaces: the serial API (SD/MA/LK/CF get+set), the Hub menu (More → Restrictions), the EX,0:0 dump, and LipSync Connect's version-gated Input-restrictions card
- Added adjustable input timing windows (upstream #62 #22 #9, roadmap item 15): the short/long/very-long input window boundaries (hardcoded 0-1 s / 1-3 s / 3-8 s since v1) are now settings — WS/WL/WM over the serial API (stored 0 = the compiled default), validated to keep short < long < max, applied at the one seam every action row is matched against; the Hub menu gets Sip & Puff → Timing (one page per window, 250 ms steps) and the sip/puff threshold pages now step a coarse 10-level scale (2/3/4/5/7/10/15/22/32/45 hPa) instead of ±1 hPa, so the mouthpiece-driven menu path is practical (the serial API and LipSync Connect keep the fine hPa granularity). The endpoints were named WS/WL/WM rather than W1/W2/W3 before shipping: LipSync Connect's response grammar matches letter-only endpoints, and a digit would have made every window response unparsable
- Added the input-state LED feedback tier (upstream #43, roadmap item 16): light mode 3 keys the LEDs to the held input's window — green in the short window, yellow after crossing into the long, red in the very-long, re-evaluated every tick; on release the LEDs return to default instead of blinking the action. Opt-in (existing tiers behave exactly as before) because re-keying the default would change semantics for every existing user; LipSync Connect offers it as "Input state". Also fixed a latent gap the tier exposed: getLightMode now keeps the live global honest (it was only ever set by writes)
- Vendored the TLV493D library as a bounded fork (upstream #37, roadmap item 1): the joystick's hall-effect sensor library moves from a zip unpacked ad hoc by CI to a vendored directory pinned by the same --libraries flag as the patched Wire. The fork bounds the two blocking constructs on the 20 ms joystick-poll path — a failed wake-up write returns an error immediately instead of delaying for a measurement that never started (the mechanism behind the JV endpoint's old device-silencing freeze), and the measurement wait is clamped to 50 ms (~5x the real master-controlled measurement, so healthy polling is unchanged). The register model and API are untouched upstream; the migration to Infineon's maintained XENSIV TLx493D library (roadmap item 2) remains the deliberate follow-up
- Root-caused the post-flash "first writes dropped" (firmware-update improvements item 2): the device was going deaf, not dropping writes — the USB-HID report paths blocked the whole main loop waiting for HID readiness (up to 5 s), and every connect-retry begin() appended a duplicate HID interface to the USB configuration (no already-begun guard in Adafruit_USBD_HID, unlike CDC), so the post-flash re-enumeration window could freeze the firmware against its serial session or present a half-configured composite device. Reports now skip instantly while the interface is not ready, and the interface registers exactly once

Version 4.3.0 | 2026-Oct-14
- Implemented cursor acceleration (upstream #86, roadmap item 9): the stored AV level (-10..10, default 0) now bends the deflection-to-speed curve in the mouse output path — level 0 is byte-for-byte the old linear behavior, positive levels move faster at gentle deflections, negative levels trade speed for precision, and full deflection always keeps the full speed of the current speed level; the level is adjustable from the Hub menu (More → Acceleration), the serial API (AV,0/AV,1, present since 4.0 but previously inert), and the app's Cursor card; also fixed the inverted comparison in decreaseJoystickAcceleration that made the level nearly impossible to lower
- Fixed the AV,1 write dispatch (found in the 2026-10-14 hardware session): the API table entry declared parameter "0" (a v4.0-era stub typo), so every AV,1 write was rejected with FAIL,3 before the function ever ran — it now accepts any value like every other setter
- After a serial-API calibration closes the Hub menu (#36), the screen now shows the "Ready to use" page instead of going blank: a merely blank screen reads as dead and invites a long wake-puff, which is the 3-8 s START_MENU input and put the menu right back (observed on hardware, 2026-10-14); the ready page says the device is finished, then clears itself after 10 s
- Screen-state correctness after asynchronous flows (upstream #36, #63 residual): the Hub menu no longer stays open after a serial-API-triggered calibration — the end page closes the menu like the pre-calibration screen — and when the USB retry loop's error episode ends because the host came back, the "No USB" page is now replaced by the ready screen once instead of lingering while the device works normally
- Added the BH,0:0 bus-health diagnostic endpoint (roadmap item 3): total bounded-timeout bus recoveries this boot, held-bus state, per-device health gates (display demoted / pressure sensors unhealthy / joystick poll backed off) and seconds since the last recovery — the telemetry that would have diagnosed the entire flaky-bus saga in minutes, now one serial read; LipSync Connect 4.3.0+ mirrors it in its health check as an "I2C bus" step
- Added the UM,1:1 update-mode entry (firmware-update improvements item 1): acks, draws a deliberate "Update mode — use the LipSync Connect app" splash as the final frame (the stock bootloader never drives the Hub's OLED, so the frozen "Restarting" message during a flash was the norm), then resets into the stock serial-DFU bootloader via the core's own enterSerialDfu(); LipSync Connect 4.3.0+ sends it over the live session in place of the 1200-baud touch when the connected firmware supports it, and a maker with a serial monitor can enter update mode with SETTINGS + UM,1:1 instead of the double-reset dance
- One short buzzer cue now plays when scroll mode or drag mode engages (upstream #61, roadmap item 16, audio half): scroll chirps higher than drag so the two are distinguishable by ear; gated to the "All" sound tier only, so "Basic" users hear no new sounds (the LED half of item 16 — cues keyed to input state rather than output action — stays on the roadmap: it changes existing feedback semantics and needs hardware validation)
- Vendored Wire: after a bounded-timeout recovery, the SDA/SCL PIN_CNF registers are restored to the begin() configuration (the NXP bus-clear leaves SCL as GPIO-output; benign under PSEL, but a recovered bus should be bit-identical to a freshly begun one), and recoveryCount()/lastRecoveryMs() expose the recovery state the BH endpoint reports (roadmap item 4)
- Added LSApiDeclarations.h (roadmap item 5): explicit declarations for every function used across .ino tab and class-header boundaries, removing the dependency on the Arduino build's auto-generated prototypes — the shallow ctags parse that a `static` local in any .ino function silently breaks, failing the build with "was not declared in this scope" inside the headers

Version 4.2.0 | 2026-Oct-13
- Cut serial settings API command latency: messages are now framed by a non-blocking line parser — newline-terminated messages are processed the instant they arrive, and legacy bare messages keep a 50 ms idle-gap frame — removing readString()'s timed busy-wait that padded every exchange with a fixed delay (1 s at the Stream default; ~2 s per command, ~30 s for LipSync Connect's settings load, now ~2 s)
- Hardened the hardware watchdog: it is now armed on every boot, including safe mode and watchdog-reset boots; a run of 3 consecutive watchdog resets (tracked in the GPREGRET2 retention register) stops re-arming so a wedged device settles in safe mode instead of resetting forever, and the budget restores after 2 minutes of uptime
- Sip and puff robustness: the once-a-minute pressure offset re-measure (and the boot-time one) now gathers its five samples one per polling tick instead of blocking the main loop for up to 15 s when a sensor misbehaves; sensors that return consecutive invalid readings are marked unhealthy — the I2C bus is left alone until a 2 s re-probe succeeds — so a flaky mouthpiece sensor can no longer stall the device, and stale readings can never fire a phantom sip or puff
- Added a patched Wire library (vendored in Build_Files/Firmware_Files/Libraries/Wire, used automatically by the CI and local builds): every nRF52 I2C transaction wait is bounded at 50 ms, and a wedged bus is recovered in place with a bounded STOP plus the NXP I2C bus-clear (up to 9 SCL clocks) — a sensor holding the bus mid-transaction now fails its read immediately instead of hanging the device until the watchdog resets it (relates to upstream issues #73 and #75)
- Hub menu and feedback no longer block the main loop: the informational screen pages (exit, mode change, center-reset and calibration completion, full-calibration and factory-reset confirmations, long-text scroll) dwell on a scheduled timer transition, and multi-tone sounds (ready, error) sequence through a note queue — the serial API, joystick and pressure polling stay live during page dwells and sound playback (the pre-restart shutdown sound keeps its deliberate blocking sequence)
- Survived a live flaky-I2C-bus hunt on the bench: a failing device on the shared bus can wedge it (bounded by Wire) or drag transfers until they crawl without ever timing out, which used to read as a flat ~1 s main-loop tax and multi-second serial exchanges. The bus now self-defends on every consumer: Wire reports held/slow state (busHealthy, recoveryCount), the joystick poll measures its own update and backs off 20 ms -> 60 s while the bus crawls, display pushes are gated by a display-health probe with one-strike demotion and exponential re-probe backoff, the no-USB retry page draws at most once per episode, the BLE connection poll is skipped outside Bluetooth mode (its isConnected() call blocked a full second on safe-mode boots), and the JV endpoint returns the last buffered reading instead of forcing a synchronous TLV493D read inside the serial command path — which, on a crawling bus, could silence the device for seconds and trip the watchdog. On the worst flaky bus the serial API now stays at ~5 ms per exchange, and the always-armed watchdog (3-strike) recovers anything that still manages to block
